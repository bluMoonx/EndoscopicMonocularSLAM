01How to read this guide

This document has two layers on purpose. You are not supposed to understand all the technical language yet — you'll grow into it as we build. But it stays in, because by the fair you'll own every word of it.

Wherever a real concept shows up, you'll see it twice:

In plain words

The version you can say out loud to a friend, a parent, or a judge who isn't a computer scientist.

The technical version

The real, correct, grown-up version — the terms, the metrics, the methods. This is the language of the abstract and the paper. Read it, let it wash over you, and it'll click as we actually do each step.

The one rule

We only build things you can explain in your own words. If you can't explain it, it doesn't go in the project. This isn't a limitation — it's the exact thing that makes a project ISEF-worthy. Judges reward a student who deeply understands a simple thing over one who parrots a complex one.

02The project in one breath

In plain words

A tiny camera goes inside the colon to look for polyps. Software watches the video and builds a 3D map of the tunnel so nothing gets missed. But the colon is wet and shiny, so the camera's own light bounces back as bright glare — and that glare confuses the software and makes it lose track. You build a filter that removes the glare before the software sees it, and you prove that removing the glare helps the software track better.

The technical version

Specular reflections from the endoscope's light source on wet mucosal tissue corrupt ORB feature extraction in monocular visual SLAM, causing trajectory drift, tracking loss, and incomplete reconstruction. Argus is a modular preprocessing pipeline inserted upstream of ORB-SLAM3 — an adaptive per-frame specularity mask followed by a Lucas–Kanade optical-flow consistency filter — evaluated as a controlled variable in an ablation study against baseline and prior-work conditions.

That's the whole project. Everything else in this guide is just how we prove it and how we make it stand out.

03The big correction — read this one

The original AI-written plan assumed we'd grade the camera's path using a score called ATE on the Hamlyn dataset. We researched it hard, and that assumption is broken. Catching it now, in week one, is a win — it would have sunk the project in September.

In plain words

To grade how well the software guessed the camera's path, you need an answer key — the true path the camera actually took. For the Hamlyn colon videos, nobody ever recorded that true path. There is no answer key. So you literally cannot grade the path on Hamlyn.

The technical version

Hamlyn ships depth / scene-structure ground truth (from Libelas stereo matching), never a 6-DOF camera trajectory. No mainstream Hamlyn paper reports a true trajectory ATE against pose GT — they report reconstruction error against stereo structure, or switch to pose-GT datasets (SCARED, EndoSLAM). The much-quoted "1.37 RMSE" for ORB-SLAM3 is a reconstruction error in millimetres, not ATE. VSLAM-LAB's Hamlyn "ground truth" file is an empty placeholder (header row only).

Our fix: measure what actually exists

In plain words

Instead of grading the path on Hamlyn, we measure things we can see directly from the software with no answer key needed — like "how long does it keep track before getting lost." Those work on every glare-y colon video, immediately. Then, for one honest path grade, we borrow a second free dataset (EndoSLAM) where researchers did record the true path.

The technical version

Primary evidence = ground-truth-free tracking metrics on Hamlyn (feature-track length, tracking-failure / relocalization rate, map-point count). Trajectory validation = ATE with evo (Sim(3)-aligned, scale-corrected for monocular) on EndoSLAM ex-vivo, which has genuine 6-DOF pose GT. Optional secondary = reconstruction RMSE vs Hamlyn Libelas depth.

04What you're actually measuring

These are your dependent variables — the things you compare before vs after glare removal. Three of them need no answer key; one uses the borrowed EndoSLAM answer key.

The no-answer-key trio (your backbone)

In plain words

1. Track length — how many video frames in a row the software follows a single spot before losing it. Glare should make this shorter.
2. Lost rate — how often the software throws up its hands and says "I don't know where I am." Glare should make this higher.
3. Map pieces — how much of the 3D map it managed to build. Glare should make this smaller.

The technical version

Feature-track length (mean consecutive frames an ORB feature survives), tracking-failure rate (fraction of frames in LOST state + relocalization count), and map-point count / density — all read directly from ORB-SLAM3's output, no GT required. These directly probe the causal mechanism: glare → corrupted correspondences → shortened tracks → lost pose.

The one real path grade

In plain words

On EndoSLAM (which has the answer key), we compute the actual grade for the guessed path vs the true path. Lower = the guess was closer to reality.

The technical version

ATE (Absolute Trajectory Error), reported as RMSE — root-mean-square distance between estimated and ground-truth camera positions after Sim(3) alignment (monocular is up-to-scale, so scale correction is mandatory). Computed with the evo library. Optional companion: RPE (Relative Pose Error) for local drift.

05The experiment

In plain words

You run the same videos four ways and compare. Only one thing changes between runs — how you treat the glare — so any difference in the scores is caused by the glare handling, nothing else. That "change only one thing" design is what makes it real science instead of a demo.

The technical version

Independent variable = preprocessing condition. Dependent variables = the metrics in §04. This is an ablation study — you toggle pieces on and off to isolate each part's contribution.

  1. Baseline — raw video into SLAM, no glare handling. Your control.
  2. Prior work — a plain fixed brightness threshold (paint over the brightest pixels). Replicates the closest existing method.
  3. Your mask — a smarter per-frame adaptive threshold that adjusts to how bright each frame is.
  4. Full pipeline — your mask plus the optical-flow motion filter that removes leftover glare that moves inconsistently with the tissue.

06What makes it ISEF-worthy

You don't reach ISEF by piling on complicated parts. You reach it with one or two things you can still explain, done rigorously. Here's the ladder — climb it in order, and stop wherever your time runs out.

Rung 1 · the centerpiece · do this

The severity curve

Plain: The glarier a video is, the more the software struggles — and your filter helps the glarier videos the most. You measure how glare-y each video is, then draw it as a graph.

Technical: Compute a per-sequence specularity-severity score (mean fraction of specular pixels/frame, measured before masking). Plot severity vs metric-improvement across sequences. A positive trend is evidence that specularity causes tracking failure — not just correlates with it.

Why it's the wow: it turns "I made a filter" into "I proved something, and I can predict how much." That one graph is your project's spine.

Rung 2 · the flagship · do this if the base works

Guessing what's under the glare

Plain: Instead of just covering glare with a black patch, use image tools (and optionally a small AI depth model) to guess what the tissue underneath probably looks like, and paint that in.

Technical: Add an inpainting condition. Start with classical cv2.inpaint (free, CPU); optionally upgrade to depth-guided inpainting using Depth-Anything-v2-Small (fits your GPU). Real open question: do synthesized pixels help or hurt trajectory accuracy?

Why it lifts you: visually striking on a poster, and it asks a question nobody has answered. This is your ISEF differentiator.

Rung 3 · the stretch · only if time

The blind-spot map

Plain: A heat-map showing which parts of the colon the camera never got a clean look at because glare was in the way — exactly what a doctor cares about.

Technical: Project low-coverage / tracking-loss regions back onto the frame as an overlay. Frame it honestly as a proof-of-concept visualization, not a validated clinical tool — that honesty is what keeps it defensible.

Why it's a stretch: great medical story, but the weakest to defend technically. Keep it modest and secondary.

07Your computer & what runs where

08The data

Two datasets, both free and legitimate. (Your instinct to distrust random GitHub links was right — but these two are the real, cited sources.)

Hamlyn — your glare testbed

Real in-body endoscopic video, wet and glare-heavy — the right place to tell the specular story. Two safe mirrors: Recasens/HamlynRectifiedDataset (20 videos, depth ground truth, from the Endo-Depth-and-Motion authors) and vslamlab/Hamlyn_Rectified_Dataset (rectified sequences + calibration, from the VSLAM-LAB benchmark team). You use the left-camera images as your single-camera input; depth is there for the optional reconstruction metric. No trajectory answer key — that's expected (§03).

EndoSLAM — your one real path grade

CapsuleEndoscope/EndoSLAM — ex-vivo GI recordings with genuine 6-DOF camera pose ground truth (captured on a controlled rig), free, no access paperwork. This is where your ATE number comes from. (A tougher, more clinical option, SCARED, exists but needs registration/a license — save it for later if at all.)

09The roadmap

Six phases, roughly nine weeks to the mid-October target. Dates are targets, not promises — Phase 2 is the crux, where most projects stall, so protect time for it. If you fall behind, drop Rung 2/3 novelty before you cut corners on rigor.

  1. Now · ~1.5 weeks

    Setup & understanding

    Finish the Python environment, download both datasets, pull a Docker ORB-SLAM3 image, and get comfortable with the five core ideas.

    Done when: you can run ORB-SLAM3 on one test clip and watch a trajectory come out the other end.

  2. Late August · ~2 weeks · the crux

    Baseline results

    Run raw (no-filter) SLAM on your chosen Hamlyn sequences and on EndoSLAM. Collect the no-answer-key metrics; compute a real ATE on EndoSLAM with evo.

    Done when: you have a baseline number for every metric on every sequence.

  3. Early September · ~2 weeks

    Build the glare filter

    Implement conditions 2–4 (fixed threshold, your adaptive mask, mask + optical-flow). Re-run everything, build the full results table.

    Done when: all four conditions are measured across all sequences.

  4. Mid September · ~1 week

    The centerpiece

    Compute the per-sequence severity score, plot the severity curve, run the paired significance tests.

    Done when: the severity graph exists and the improvement is statistically tested.

  5. Late September · ~1.5 weeks

    The flagship (if on track)

    Add inpainting as a fifth condition and answer: does guessing-the-hidden-tissue help or hurt?

    Done when: you have a clear result for the inpainting question — even "it hurts" is a finding.

  6. Early October → fair · ongoing

    Blind-spot map + write-up

    Optional blind-spot visualization, then poster, abstract, and paperwork. Keep the research notebook current the whole time — start it in Phase 1, not now.

    Done when: results are frozen and the presentation materials are underway.

10The fair & the paperwork

In plain words

The path is regional → state → international: GSDSEF → CSEF → ISEF. The boring-but-critical rule: you usually need your fair's review committee to approve your plan before you start experimenting. The good news — because you use public, already-recorded data and no live patients or animals, your review is normally the light kind.

The technical version

Get SRC/IRB approval before experimentation (an ISEF requirement). Using a pre-existing, publicly available, de-identified dataset with no human/animal subject interaction generally means the lighter review track — but you still complete the core ISEF forms (Adult Sponsor Checklist 1, Student Checklist 1A, Research Plan, Approval Form 1B) and confirm each dataset's license permits research use. Verify the current-year specifics with your fair coordinator — don't take these form numbers as final.

Category call (decide later): Computer Science / Systems Software plays up the engineering; Biomedical plays up the medical impact. We'll pick once results are in and we see which story is stronger. Start the research notebook in Phase 1 — judges and SRC both want to see the dated trail, and reconstructing it later is misery.

11Honest verdict

Doable on your machine and your timeline. A strong regional/state project as its base — with a real, not-guaranteed shot at ISEF.

The base project (glare hurts tracking → removing it helps, shown with the no-answer-key metrics + one real ATE) is solidly CSEF-competitive. Three things lift it toward ISEF: (1) the severity curve landing as a clean, real result; (2) the inpainting flagship, if you get there; and (3) you understanding and defending every piece in the interview.

It's more technical and more rigorous than last year's project — the kind of rigorous evaluation study that ISEF finalists in this category actually are. The honest risk isn't the idea; it's execution: getting the pipeline running, and whether the results come out clean. That's why we sequence by risk and win the boring version first.

12Glossary

This grows as we go. Every term here you'll be able to explain by the fair.

SLAM
The mapping software. Works out where the camera is and what the space looks like, from video alone. (Simultaneous Localization And Mapping.)
ORB-SLAM3
The specific, well-known SLAM program you'll use. Runs on the CPU. "ORB" is the type of visual landmark it tracks.
Feature / landmark
A small distinctive spot the software locks onto and follows across frames. SLAM lives or dies by these.
Specular / glare
The bright shiny reflections off wet tissue. The villain of your story.
Track / tracking loss
The software successfully following its landmarks over time. Glare makes it "lose track."
Monocular
Using one camera (one lens). Harder than two, because one eye can't judge true distance — so the map has no fixed scale.
Ground truth
The answer key: the true thing, used to grade the software's guess.
ATE
Absolute Trajectory Error — the grade for the guessed path vs the true path. Lower is better. Needs an answer key.
RMSE
Root-Mean-Square Error — a standard way to average error that punishes big misses more than small ones.
Ablation
Turning parts of your system on and off to see how much each part actually contributes.
evo
A free Python tool that lines up two paths and computes ATE/RPE for you.
Optical flow
Measuring how each spot moves between two frames. Glare moves differently from tissue — that's how stage 2 catches it.
Inpainting
Filling in a hole in an image with a plausible guess of what belongs there.
Severity score
Your "how glare-y is this video" number — the fraction of glare pixels per frame, averaged.
